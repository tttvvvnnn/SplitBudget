# Как устроен релиз и версионирование

## Версии

Используется [SemVer](https://semver.org/lang/ru/): `vMAJOR.MINOR.PATCH`, например `v1.2.0`.

- **MAJOR** (`v2.0.0`) — несовместимые изменения: сломали API, которым мог бы пользоваться
  кто-то ещё, или миграция БД требует ручных действий на проде (не просто `alembic upgrade head`).
- **MINOR** (`v1.3.0`) — новая функциональность, обратно совместимая (новая вкладка в mini app,
  новый эндпоинт).
- **PATCH** (`v1.2.4`) — исправление багов, без новой функциональности.

Версия, которая реально крутится на сервере, видна в `GET /healthz` (`{"status": "ok", "version": "1.2.0"}`)
— полезно свериться после деплоя, что раскатилось именно то, что ожидали.

## Ветки

- `main` — всегда рабочий код (CI гоняет тесты на каждый пуш/PR), но **не деплоится
  автоматически**. Копите здесь изменения между релизами.
- Фичи — по желанию через отдельные ветки + Pull Request в `main` (тогда CI проверит их до
  мёржа), либо коммитьте в `main` напрямую, если работаете соло — на процесс релиза это не влияет.
- Тег `vX.Y.Z` на `main` — то, что реально уезжает на сервер (`.github/workflows/release.yml`).

## Как выпустить релиз

1. Убедитесь, что `main` зелёный — вкладка **Actions** репозитория, workflow `CI`.

2. Если менялись модели в `app/shared/models.py` — создайте миграцию и закоммитьте её
   (миграции обязаны попасть в релиз вместе с кодом, который на них рассчитывает):

   ```bash
   pip install -r requirements-dev.txt
   alembic revision --autogenerate -m "краткое описание изменения"
   # откройте новый файл в migrations/versions/ и проверьте, что Alembic сгенерировал то, что нужно
   git add migrations/
   ```

3. Обновите `CHANGELOG.md` — перенесите пункты из `## [Unreleased]` в новый раздел
   `## [X.Y.Z] - YYYY-MM-DD`, оставив `## [Unreleased]` пустым сверху для следующих изменений.

4. Закоммитьте и затегируйте:

   ```bash
   git add CHANGELOG.md
   git commit -m "chore(release): v1.2.0"
   git tag -a v1.2.0 -m "v1.2.0"
   git push origin main
   git push origin v1.2.0
   ```

5. Дальше всё сделает `release.yml`: тесты → образ в ghcr.io → релиз на GitHub (с
   автоматически сгенерированными release notes по коммитам) → деплой на сервер по SSH.
   Прогресс — вкладка **Actions**. Проверить, что раскатилось нужное: `curl https://ваш-домен/healthz`.

## Хотфикс поверх старого релиза

Если в `main` уже накопились незавершённые изменения, а нужно срочно пофиксить баг именно в
том, что сейчас на проде:

```bash
git checkout -b hotfix/v1.2.1 v1.2.0   # ветка от последнего релизного тега, не от main
# правите баг, коммитите
git tag -a v1.2.1 -m "v1.2.1"
git push origin hotfix/v1.2.1 v1.2.1   # тег запустит release.yml и задеплоит фикс
# затем перенесите фикс и в main (cherry-pick или merge), чтобы он не потерялся
git checkout main
git cherry-pick <commit-фикса>
git push origin main
```

## Откат

Если релиз оказался с багом — см. раздел «Откат на предыдущую версию» в `DEPLOYMENT.md`:
это просто передеплой предыдущего тега, без пересборки.
